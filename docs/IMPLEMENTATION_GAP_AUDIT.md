# GitOpt Implementation Gap Audit

## Purpose

This document records the gap analysis performed against the current GitOpt implementation and the product flow described by the frontend specification:

> repository characteristics → workload → detected bottleneck → Git mechanism → measurable/estimated improvement → actionable configuration

The audit focuses on the end-to-end path required for the MVP:

1. Register a repository.
2. Collect repository evidence in the backend.
3. Display those metrics in the frontend analysis screens.
4. Evaluate workload-specific recommendations.
5. Explain why each recommendation matched.
6. Generate concrete Git commands/configuration.
7. Let the user download the generated templates/report.

## Executive summary

Before this integration pass, the frontend and backend were connected at the route level, but the product was not connected at the **data-truth level**. Most screens could render successfully even when repository analysis had not happened because both layers substituted Microsoft/Git demo values. This made the application appear functional while hiding API, analysis, and data-quality failures.

The integration branch removes that behavior. Repository evidence now originates in a backend collector, analysis results carry provenance, the frontend renders the returned data without demo substitutions, recommendations are generated by the existing deterministic rules engine, and generated templates can be downloaded.

## Backend analysis contract

An analysis is the source of truth for the frontend. Important fields now include:

```ts
interface AnalysisItem {
  id: string
  repository_id: string
  status: 'pending' | 'analyzing' | 'completed' | 'failed'
  progress_percent?: number
  current_stage?: string
  optimization_score?: number
  metrics?: MetricItem[]
  object_distribution?: ObjectDistribution
  largest_objects?: LargestObjectItem[]
  metric_source?: 'github_api' | 'git_cli' | 'simulated'
  metric_notes?: string[]
  default_branch?: string
  tree_truncated?: boolean
}
```

The intended frontend rule is simple:

**Do not infer or substitute repository metrics in React. If a backend metric is unavailable, show it as unavailable.**

## GitHub metrics currently collected

For GitHub repositories, the backend collects:

- GitHub-reported repository size.
- Default branch.
- Commit count for the analyzed branch.
- Branch count.
- Current/default-tree file count.
- Files at or above 10 MB in the current/default tree.
- Largest files exposed by the recursive tree response.
- Current-tree file payload.
- An observed object-evidence count based on commits + current tree entries.
- A clone-time estimate derived from repository size.

### Important interpretation rules

The GitHub API cannot reproduce every value produced by local Git plumbing without actually cloning the repository. Therefore:

- GitHub repository size is reported evidence, not a measured clone payload.
- File metrics describe the current/default tree, not every historical blob.
- The observed object count is not equivalent to `git count-objects`.
- Clone time is estimated and must not be labelled measured.
- GitHub may truncate very large recursive tree responses; the analysis exposes that condition and the UI warns that file metrics are lower bounds.

For local repositories, GitOpt can use Git CLI directly and `git count-objects -v` gives stronger object-database evidence.

## Recommendation architecture

The existing deterministic rules engine is retained. It is the correct architectural fit for the product because it keeps the recommendation chain explainable:

```text
repository evidence
       +
selected workload
       ↓
deterministic rule evaluation
       ↓
matched recommendation
       ↓
reasoning + relevance score + trade-offs
       ↓
generated command/config template
```

This is preferable to adding an LLM between the metrics and the recommendation decision. AI can be added later for explanation or summarization, but the optimization decision should remain inspectable and reproducible.

## Downloadable outputs

The Configuration page now builds outputs from the templates attached to the recommendations for the selected analysis.

Supported downloads:

- `<repository>-gitopt.sh` — generated shell commands.
- `<repository>.gitconfig` — generated Git configuration snippets when applicable.
- `<repository>-gitopt-report.md` — repository metrics, recommendations, estimates, generated configuration, and evidence notes.

Downloads are created in the browser from backend-generated template content. No hard-coded Microsoft/Git configuration remains in the export flow.

## Analysis lifecycle

The backend now owns analysis state:

```text
POST /api/v1/analyses
        ↓
analysis record created
status=analyzing
stage=discovery
        ↓
metadata
        ↓
metrics
        ↓
recommendations
        ↓
completed / failed
```

The frontend Progress page polls `GET /api/v1/analyses/:id` and renders the returned stage/progress. It does not advance progress using an arbitrary browser timer.

### Current runtime limitation

The MVP executes the analysis job inside the long-running Express process. This is appropriate for local development and a traditional server deployment, but a production deployment should move analysis jobs to a durable queue/worker if requests may involve large repositories or the hosting environment is serverless/ephemeral.

## Remaining architectural gaps

### 1. Durable persistence

`backend/src/config/database.ts` currently implements an in-memory relational store despite the presence of PostgreSQL-related configuration and schema assets. Analyses, repositories, recommendations and history are lost when the process restarts.

**Recommended next step:** replace the map-backed methods behind the existing database interface with PostgreSQL queries/migrations. The service layer can remain mostly unchanged.

### 2. Measured Git operation benchmarks

The strategy comparison currently applies documented model factors to the analyzed repository profile. It is useful for ranking hypotheses but is not a benchmark harness.

**Recommended next step:** create an isolated benchmark worker that runs disposable clones/checkouts and records:

- wall-clock duration,
- bytes transferred,
- resulting `.git` size,
- working-tree disk size,
- Git version,
- network/environment metadata,
- exact command/strategy.

Measured results should be persisted separately from estimates.

### 3. GitLab and arbitrary Git remotes

The API schema still understands repository source types, but the remote collector implemented in this integration pass is GitHub-specific.

**Recommended next step:** introduce a `RepositoryMetricsProvider` interface with GitHub, GitLab and local-Git implementations instead of adding provider conditionals throughout analysis logic.

### 4. Authentication model for user-owned private repositories

`GITHUB_TOKEN` is a server-level credential and is sufficient for development/admin deployments, but it is not the final multi-user authorization model.

**Recommended next step:** use a GitHub App or OAuth installation and associate repository access with the authenticated GitOpt user. Store tokens encrypted and request read-only repository scopes.

### 5. Sparse-checkout path selection

Some existing recommendation templates use a generic example path. A production-quality sparse-checkout recommendation should choose candidate directories from repository structure/workload evidence or use an explicit placeholder that the user must fill in.

### 6. Historical growth metrics

The frontend design includes repository size-over-time. The existing implementation fabricated this curve. It has been removed from the evidence path.

**Recommended next step:** collect snapshots from repeated analyses or derive historical object growth through a dedicated Git-history worker. Do not infer a time series from a single repository snapshot.

### 7. Test coverage

The rules engine has tests, but the end-to-end collector contract needs coverage for:

- GitHub URL parsing,
- public repository API responses,
- private repository 404/access errors,
- rate limits,
- empty repositories,
- recursive-tree truncation,
- analysis state transitions,
- no-recommendation cases,
- template/report downloads.

## API/UI invariants

Future changes should preserve these invariants:

1. The frontend never invents missing metrics.
2. Every recommendation is traceable to analysis evidence + workload.
3. Estimated and measured values are visibly distinguished.
4. Configuration is generated from recommendation templates, not hard-coded per screen.
5. A recommendation may legitimately return no match.
6. Analysis failures are explicit and do not silently fall back to demo data.
7. Unsupported repository providers fail with a useful message rather than generating synthetic numbers.

## Suggested implementation priority after this branch

1. Add automated integration tests around the GitHub collector and analysis lifecycle.
2. Replace the in-memory data store with PostgreSQL.
3. Build measured benchmark workers.
4. Improve sparse-checkout path discovery.
5. Add GitHub App/OAuth private-repository authorization.
6. Add GitLab provider support.
7. Add persisted analysis history and real longitudinal growth charts.

## Acceptance flow for this integration branch

A successful manual test should look like this:

1. Start backend on port 3000 and frontend on port 5173.
2. Open `/analyze`.
3. Enter a public GitHub repository.
4. Select a workload.
5. Start analysis.
6. Verify `/progress?id=<analysis>` is driven by backend stages.
7. Verify `/overview?id=<analysis>` displays repository-specific values and provenance.
8. Verify recommendations contain only matched deterministic rules.
9. Open a recommendation detail page.
10. Open Configuration and download generated shell/config/report files.
11. Verify the strategy comparison says **modelled/estimated**, not measured.
12. Repeat with a private repository after configuring `GITHUB_TOKEN` with read access.
